Django дальше: связи и представления на классах

Продолжаем список задач из первого проекта на Django. Разложим задачи по категориям — это первая связь между моделями, уберём лишние запросы к базе, перепишем представления на готовые классы Django и закрепим всё тестами. Около полутора часов.

Это продолжение варианта на Django из «Первого проекта». Про модели и миграции — в разделе «Базы данных».

Начинаем с того места, где закончился первый проект.

  • Пройденный вариант на Django (шаги 1–10). Нет своего — скачайте код первого проекта и выполните python manage.py migrate.
  • Включённое окружение .venv с Django 6.1: команда python -m django --version покажет версию.
  • Пара задач в базе — так будет видно, что после миграции старые данные остались на месте.

Как работать с шагами. Если блок подписан именем файла, замените файл целиком: так проще не пропустить импорт. Сервер runserver может работать всё время, команды вводите во втором окне терминала. Пройденные шаги сохраняются в этом браузере.

Категории, классы и тесты

Три части: связь между моделями, представления на классах и тесты к ним.

0 из 9 шагов пройдено

  1. Часть 1. Связи между моделями

    Шаг 1. Опишите категорию и свяжите с ней задачу

    Зачем отдельная модель, если можно добавить задаче текстовое поле «категория»? Текст пришлось бы писать в каждой задаче: «Учёба» и «учеба» стали бы разными категориями, а переименовать категорию пришлось бы во всех задачах по очереди. Отдельная таблица хранит каждую категорию один раз, а задача ссылается на неё по номеру. Такая связь называется «многие к одному»: у категории много задач, у задачи одна категория. В Django её описывает поле ForeignKey.

    tasks/models.py 
    from django.db import models

class Category(models.Model):
    name = models.CharField(max_length=50, unique=True)

    class Meta:
        ordering = ["name"]
        verbose_name_plural = "categories"

    def __str__(self):
        return self.name

class Task(models.Model):
    title = models.CharField(max_length=200)
    done = models.BooleanField(default=False)
    category = models.ForeignKey(
        Category,
        on_delete=models.SET_NULL,
        null=True,
        blank=True,
        related_name="tasks",
    )

    def __str__(self):
        return self.title
    tasks/admin.py 
    from django.contrib import admin

from .models import Category, Task

admin.site.register(Category)

@admin.register(Task)
class TaskAdmin(admin.ModelAdmin):
    list_display = ["title", "category", "done"]
    list_filter = ["category", "done"]
    • ForeignKey(Category, …) добавит в таблицу задач столбец category_id — номер категории.
    • on_delete=models.SET_NULL говорит, что делать с задачами, когда категорию удаляют: оставить их без категории. CASCADE удалил бы задачи вместе с категорией, PROTECT запретил бы удалять категорию, пока в ней есть задачи.
    • null=True разрешает пустое значение в базе: у задач из первого проекта категории нет. blank=True разрешает оставить поле пустым в форме.
    • related_name="tasks" — имя обратной связи: у каждой категории появится список её задач category.tasks. Он пригодится в шаге 3.
    • unique=True не даст завести две одинаковые категории, а ordering выводит категории по алфавиту везде, где их показывают.
    • TaskAdmin показывает категорию в списке задач админки и добавляет фильтр по категории и отметке «готово».

    Ожидаемый результат

    Проверка кода проходит:

    System check identified no issues (0 silenced).

    А вот главная страница, если сервер запущен, пока отвечает ошибкой no such column: tasks_task.category_id: модель уже знает о новом поле, а таблица в базе — ещё нет. Это исправит миграция в следующем шаге.

  2. Шаг 2. Перенесите изменения в базу

    Команда makemigrations сравнивает модели с прошлыми миграциями и записывает разницу в новый файл — это план изменений. migrate выполняет план: создаёт таблицу категорий и добавляет столбец в таблицу задач. Вопросов Django не задаст: благодаря null=True у старых задач можно оставить категорию пустой. Без него makemigrations спросил бы, что записать в уже существующие строки (см. частые ошибки).

    Терминал 
    python manage.py makemigrations
python manage.py migrate

    Ожидаемый результат

    Первая команда создала файл миграции:

    Migrations for 'tasks':
  tasks/migrations/0002_category_task_category.py
    + Create model Category
    + Add field category to task

    Вторая применила его:

    Operations to perform:
  Apply all migrations: admin, auth, contenttypes, sessions, tasks
Running migrations:
  Applying tasks.0002_category_task_category... OK

    Старые задачи остались на месте, только категории у них пока нет. Главная страница снова открывается.

    Откройте консоль Django и вводите строки по одной. Django 6.1 сам импортирует модели в консоль, писать import не нужно.

  4. Шаг 4. Выберите категорию в форме и отфильтруйте список

    В форму добавляем поле category: ModelForm сам сделает из него выпадающий список категорий из базы. labels задаёт подписи полей по-русски — без них Django показал бы имена полей Title и Category. Новое представление category показывает задачи одной категории. Замените четыре файла целиком.

    tasks/forms.py 
    from django import forms

from .models import Task

class TaskForm(forms.ModelForm):
    class Meta:
        model = Task
        fields = ["title", "category"]
        labels = {"title": "Задача", "category": "Категория"}
    tasks/views.py 
    from django.shortcuts import get_object_or_404, redirect, render
from django.views.decorators.http import require_POST

from .forms import TaskForm
from .models import Category, Task

def index(request):
    if request.method == "POST":
        form = TaskForm(request.POST)
        if form.is_valid():
            form.save()
            return redirect("index")
    else:
        form = TaskForm()
    return render(request, "tasks/index.html", {
        "tasks": Task.objects.all(),
        "categories": Category.objects.all(),
        "form": form,
    })

def category(request, pk):
    current = get_object_or_404(Category, pk=pk)
    return render(request, "tasks/index.html", {
        "tasks": current.tasks.all(),
        "categories": Category.objects.all(),
        "current": current,
        "form": TaskForm(initial={"category": current}),
    })

@require_POST
def toggle(request, pk):
    task = get_object_or_404(Task, pk=pk)
    task.done = not task.done
    task.save()
    return redirect("index")

@require_POST
def delete(request, pk):
    get_object_or_404(Task, pk=pk).delete()
    return redirect("index")

  5. Шаг 5. Уберите лишние запросы: select_related

    Шаблон выводит {{ task.category.name }} у каждой задачи. Task.objects.all() загружает только задачи, а за категорией каждой задачи Django сходит в базу отдельно — в тот момент, когда шаблон к ней обратится. Три задачи — четыре запроса, сто задач — сто один. Это называют проблемой N+1: страница тормозит тем сильнее, чем больше данных. Посчитаем запросы в консоли:

    python manage.py shell 
    from django.db import connection
from django.test.utils import CaptureQueriesContext
with CaptureQueriesContext(connection) as queries:
    names = [str(task.category) for task in Task.objects.all()]

len(queries)
with CaptureQueriesContext(connection) as queries:
    names = [str(task.category) for task in Task.objects.select_related("category")]

len(queries)
print(queries[0]["sql"])

    select_related("category") соединяет две таблицы в одном запросе (LEFT OUTER JOIN), и задачи приходят сразу с категориями. Замените в tasks/views.py функцию index: изменилась одна строка, "tasks": ….

    tasks/views.py — функция index 
    def index(request):
    if request.method == "POST":
        form = TaskForm(request.POST)
        if form.is_valid():
            form.save()
            return redirect("index")
    else:
        form = TaskForm()
    return render(request, "tasks/index.html", {
        "tasks": Task.objects.select_related("category"),
        "categories": Category.objects.all(),
        "form": form,
    })

    На странице категории так делать не нужно: задачи взяты через current.tasks, и Django уже знает их категорию, поэтому лишних запросов там нет. Для обратной стороны связи — например, вывести у каждой категории её задачи — есть prefetch_related: он загружает всё вторым запросом.

    Ожидаемый результат

    Без select_related — четыре запроса, с ним — один:

    >>> from django.db import connection
>>> from django.test.utils import CaptureQueriesContext
>>> with CaptureQueriesContext(connection) as queries:
...     names = [str(task.category) for task in Task.objects.all()]
...
>>> len(queries)
4
>>> with CaptureQueriesContext(connection) as queries:
...     names = [str(task.category) for task in Task.objects.select_related("category")]
...
>>> len(queries)
1
>>> print(queries[0]["sql"])

    Число у вас может отличаться: без select_related получается один запрос плюс по одному на каждую задачу с категорией. За пустой категорией старых задач Django в базу не ходит. Пустая строка после ... — нажатие Enter, которое закрывает блок with.

  6. Часть 2. Представления на классах

    Шаг 6. Добавление задачи — CreateView

    Функция index сейчас делает две работы: показывает список (GET) и сохраняет форму (POST). Для типовой работы в Django есть готовые классы — обобщённые представления. Начнём с сохранения: CreateView сам создаёт форму, проверяет её, сохраняет задачу и перенаправляет. Нам остаётся указать модель, форму и адрес возврата.

    tasks/views.py 
    from django.shortcuts import get_object_or_404, redirect, render
from django.urls import reverse_lazy
from django.views.decorators.http import require_POST
from django.views.generic import CreateView

from .forms import TaskForm
from .models import Category, Task

def index(request):
    return render(request, "tasks/index.html", {
        "tasks": Task.objects.select_related("category"),
        "categories": Category.objects.all(),
        "form": TaskForm(),
    })

def category(request, pk):
    current = get_object_or_404(Category, pk=pk)
    return render(request, "tasks/index.html", {
        "tasks": current.tasks.all(),
        "categories": Category.objects.all(),
        "current": current,
        "form": TaskForm(initial={"category": current}),
    })

class TaskCreateView(CreateView):
    model = Task
    form_class = TaskForm
    success_url = reverse_lazy("index")

@require_POST
def toggle(request, pk):
    task = get_object_or_404(Task, pk=pk)
    task.done = not task.done
    task.save()
    return redirect("index")

@require_POST
def delete(request, pk):
    get_object_or_404(Task, pk=pk).delete()
    return redirect("index")

  7. Шаг 7. Список — ListView

    Теперь заменим одним классом и index, и category. Обе страницы показывают один шаблон, разница лишь в том, какие задачи взять. ListView берёт список из метода get_queryset(), поэтому один класс обслуживает оба маршрута: на странице категории в self.kwargs лежит pk из адреса.

    tasks/views.py 
    from django.shortcuts import get_object_or_404, redirect
from django.urls import reverse_lazy
from django.views.decorators.http import require_POST
from django.views.generic import CreateView, ListView

from .forms import TaskForm
from .models import Category, Task

class TaskListView(ListView):
    template_name = "tasks/index.html"
    context_object_name = "tasks"

    def get_queryset(self):
        self.current = None
        if "pk" in self.kwargs:
            self.current = get_object_or_404(Category, pk=self.kwargs["pk"])
            return self.current.tasks.all()
        return Task.objects.select_related("category")

    def get_context_data(self, **kwargs):
        context = super().get_context_data(**kwargs)
        context["categories"] = Category.objects.all()
        context["current"] = self.current
        context["form"] = TaskForm(initial={"category": self.current})
        return context

class TaskCreateView(CreateView):
    model = Task
    form_class = TaskForm
    success_url = reverse_lazy("index")

@require_POST
def toggle(request, pk):
    task = get_object_or_404(Task, pk=pk)
    task.done = not task.done
    task.save()
    return redirect("index")

@require_POST
def delete(request, pk):
    get_object_or_404(Task, pk=pk).delete()
    return redirect("index")
    mysite/urls.py 
    from django.contrib import admin
from django.urls import path

from tasks import views

urlpatterns = [
    path("admin/", admin.site.urls),
    path("", views.TaskListView.as_view(), name="index"),
    path("category/<int:pk>/", views.TaskListView.as_view(), name="category"),
    path("tasks/add/", views.TaskCreateView.as_view(), name="add"),
    path("tasks/<int:pk>/toggle/", views.toggle, name="toggle"),
    path("tasks/<int:pk>/delete/", views.delete, name="delete"),
]
    • template_name — наш шаблон вместо имени по умолчанию tasks/task_list.html. context_object_name = "tasks" — имя списка в шаблоне (по умолчанию object_list), поэтому шаблон менять не нужно.
    • get_queryset() решает, какие задачи показать: на главной все, сразу с категориями, в категории — current.tasks.all().
    • get_context_data() добавляет в шаблон то, что к списку не относится: категории для ссылок, текущую категорию и пустую форму.
    • toggle и delete остаются функциями: шаблон и форма им не нужны, и пять строк функции понятнее класса. Классы выгодны там, где работа типовая.

    tasks/tests.py 
    from django.test import TestCase
from django.urls import reverse

from .models import Category, Task

class TaskViewsTests(TestCase):
    @classmethod
    def setUpTestData(cls):
        cls.study = Category.objects.create(name="Учёба")
        cls.home = Category.objects.create(name="Дом")
        Task.objects.create(title="Сдать лабораторную", category=cls.study)
        Task.objects.create(title="Вынести мусор", category=cls.home)
        Task.objects.create(title="Без категории")

    def test_list_shows_all_tasks(self):
        response = self.client.get(reverse("index"))
        self.assertEqual(response.status_code, 200)
        self.assertTemplateUsed(response, "tasks/index.html")
        self.assertEqual(len(response.context["tasks"]), 3)

    def test_category_shows_only_its_tasks(self):
        response = self.client.get(reverse("category", args=[self.study.pk]))
        self.assertContains(response, "Сдать лабораторную")
        self.assertNotContains(response, "Вынести мусор")

    def test_unknown_category_is_404(self):
        response = self.client.get(reverse("category", args=[999]))
        self.assertEqual(response.status_code, 404)

    def test_create_saves_task_and_redirects(self):
        response = self.client.post(reverse("add"), {"title": "Полить цветы", "category": self.home.pk})
        self.assertRedirects(response, reverse("index"))
        self.assertTrue(self.home.tasks.filter(title="Полить цветы").exists())

    def test_create_rejects_empty_title(self):
        response = self.client.post(reverse("add"), {"title": ""})
        self.assertEqual(response.status_code, 200)
        self.assertIn("title", response.context["form"].errors)
        self.assertEqual(Task.objects.count(), 3)

    def test_list_needs_same_queries_for_any_number_of_tasks(self):
        for number in range(10):
            Task.objects.create(title=f"Задача {number}", category=self.study)
        with self.assertNumQueries(3):
            self.client.get(reverse("index"))

Проверь себя

Ответьте мысленно, затем откройте ответ.

Зачем у ForeignKey стоит null=True?

В базе уже были задачи из первого проекта, и у них нет категории. null=True разрешает оставить в столбце category_id пустое значение, поэтому миграция прошла без вопросов. Без него makemigrations потребовал бы значение по умолчанию для старых строк.

Что станет с задачами, если удалить категорию «Дом»?

Задачи останутся, у них просто пропадёт категория: так велит on_delete=models.SET_NULL. Удаление вернёт (1, {'tasks.Category': 1}) — удалена одна категория и ни одной задачи. С CASCADE вместе с категорией удалились бы и её задачи, с PROTECT Django не дал бы удалить категорию, пока в ней есть задачи.

Чем select_related отличается от prefetch_related?

select_related соединяет таблицы в одном SQL-запросе (JOIN) и подходит, когда у каждой записи один связанный объект: у задачи одна категория. prefetch_related делает второй запрос и раскладывает результаты по объектам в Python — он нужен для обратной связи и «многие ко многим», например, чтобы вывести у каждой категории все её задачи.

Почему после перехода на ListView форма, отправленная на главную, получает ответ 405?

ListView умеет отвечать только на чтение — GET (и служебные HEAD и OPTIONS). На POST он отвечает «Method Not Allowed». Сохранение теперь живёт в TaskCreateView по адресу /tasks/add/, туда форма и должна отправляться.

Зачем в ListView указали context_object_name = "tasks"?

По умолчанию список попадает в шаблон под именами object_list и task_list. Наш шаблон с первого проекта перебирает tasks, и одна строка в классе избавляет от правки шаблона.

Частые ошибки и как их исправить

Сообщения приведены так, как их показывает Django 6.1. Нажмите на ошибку, чтобы увидеть решение.

«no such column: tasks_task.category_id»

django.db.utils.OperationalError: no such column: tasks_task.category_id Модель уже знает о поле category, а в таблице базы столбца ещё нет. Выполните шаг 2: python manage.py makemigrations и python manage.py migrate.

makemigrations: «It is impossible to add a non-nullable field 'category'»

It is impossible to add a non-nullable field 'category' to task without specifying a default. This is because the database needs something to populate existing rows. У поля нет null=True, а в таблице уже есть задачи: базе нечего записать в их новый столбец. Выберите вариант 2 (Quit and manually define a default value in models.py), добавьте полю null=True, blank=True, как в шаге 1, и запустите makemigrations снова.

«'Category' object has no attribute 'task_set'»

AttributeError: 'Category' object has no attribute 'task_set' Имя task_set Django даёт обратной связи, только пока у ForeignKey нет related_name. У нас related_name="tasks", поэтому задачи категории — category.tasks.all().

«Method Not Allowed (POST): /» и ответ 405

Method Not Allowed (POST): / Форма добавления отправляется на главную, а там теперь ListView, который принимает только GET. Проверьте в index.html строку формы: <form method="post" action="{% url 'add' %}"> (шаг 6).

«TemplateDoesNotExist: tasks/task_form.html»

django.template.exceptions.TemplateDoesNotExist: tasks/task_form.html CreateView показывает этот шаблон, когда форма не прошла проверку, или при открытии /tasks/add/. Создайте файл tasks/templates/tasks/task_form.html из шага 6 — имя складывается из названия модели и окончания _form.

«Reverse for 'add' not found»

django.urls.exceptions.NoReverseMatch: Reverse for 'add' not found. 'add' is not a valid view function or pattern name. Шаблон ссылается на маршрут add, а в mysite/urls.py его нет. Добавьте строку path("tasks/add/", views.TaskCreateView.as_view(), name="add").

Тест: «AssertionError: 15 != 3 : 15 queries executed, 3 expected»

AssertionError: 15 != 3 : 15 queries executed, 3 expected На главной снова проблема N+1: в get_queryset пропал select_related("category"), или шаблон обращается к другой связи, которую не загрузили заранее. Верните select_related, как в шаге 7.
