Django next steps: relations and class-based views

We continue the task list from the first Django project. We will sort tasks into categories — your first relation between models — remove extra database queries, rewrite the views with Django's ready-made classes and back it all up with tests. About an hour and a half.

This continues the Django track of the “First project”. Models and migrations are covered in “Databases”.

  1. Part 1. Relations between models

    Step 1. Describe a category and link tasks to it

    Why a separate model if we could just give a task a text field “category”? We would have to type the text in every task: “Учёба” and “учеба” would become different categories, and renaming a category would mean editing every task one by one. A separate table stores each category once, and a task refers to it by its number. This kind of relation is called “many-to-one”: a category has many tasks, a task has one category. In Django it is described by a ForeignKey field.

    tasks/models.py 
    from django.db import models

class Category(models.Model):
    name = models.CharField(max_length=50, unique=True)

    class Meta:
        ordering = ["name"]
        verbose_name_plural = "categories"

    def __str__(self):
        return self.name

class Task(models.Model):
    title = models.CharField(max_length=200)
    done = models.BooleanField(default=False)
    category = models.ForeignKey(
        Category,
        on_delete=models.SET_NULL,
        null=True,
        blank=True,
        related_name="tasks",
    )

    def __str__(self):
        return self.title
    tasks/admin.py 
    from django.contrib import admin

from .models import Category, Task

admin.site.register(Category)

@admin.register(Task)
class TaskAdmin(admin.ModelAdmin):
    list_display = ["title", "category", "done"]
    list_filter = ["category", "done"]
    • ForeignKey(Category, …) adds a category_id column — the category number — to the tasks table.
    • on_delete=models.SET_NULL says what to do with tasks when their category is deleted: keep them without a category. CASCADE would delete the tasks together with the category, and PROTECT would forbid deleting a category that still has tasks.
    • null=True allows an empty value in the database: tasks from the first project have no category. blank=True allows the field to be left empty in a form.
    • related_name="tasks" is the name of the reverse relation: every category gets the list of its tasks, category.tasks. It comes in handy in step 3.
    • unique=True prevents two identical categories, and ordering lists categories alphabetically wherever they are shown.
    • TaskAdmin shows the category in the admin's task list and adds filters by category and by the “done” mark.

  2. Step 2. Apply the changes to the database

  5. Step 5. Remove extra queries: select_related

    The template prints {{ task.category.name }} for every task. Task.objects.all() loads only the tasks, and Django fetches each task's category with a separate query — at the moment the template asks for it. Three tasks mean four queries, a hundred tasks mean a hundred and one. This is called the N+1 problem: the more data, the slower the page. Let's count the queries in the shell:

    python manage.py shell 
    from django.db import connection
from django.test.utils import CaptureQueriesContext
with CaptureQueriesContext(connection) as queries:
    names = [str(task.category) for task in Task.objects.all()]

len(queries)
with CaptureQueriesContext(connection) as queries:
    names = [str(task.category) for task in Task.objects.select_related("category")]

len(queries)
print(queries[0]["sql"])

    select_related("category") joins the two tables in one query (LEFT OUTER JOIN), and the tasks arrive together with their categories. Replace the index function in tasks/views.py: one line changed, "tasks": ….

    tasks/views.py — the index function 
    def index(request):
    if request.method == "POST":
        form = TaskForm(request.POST)
        if form.is_valid():
            form.save()
            return redirect("index")
    else:
        form = TaskForm()
    return render(request, "tasks/index.html", {
        "tasks": Task.objects.select_related("category"),
        "categories": Category.objects.all(),
        "form": form,
    })

    The category page does not need this: its tasks come from current.tasks, and Django already knows their category, so there are no extra queries there. For the other side of the relation — for example, listing each category's tasks — there is prefetch_related: it loads everything with a second query.

    Expected result

    Without select_related there are four queries, with it — one:

  6. Part 2. Class-based views

    Step 6. Adding a task — CreateView

    The index function currently does two jobs: it shows the list (GET) and saves the form (POST). For routine work Django has ready-made classes — generic views. Let's start with saving: CreateView creates the form, validates it, saves the task and redirects by itself. All we specify is the model, the form and where to go back to.

    tasks/views.py 
    from django.shortcuts import get_object_or_404, redirect, render
from django.urls import reverse_lazy
from django.views.decorators.http import require_POST
from django.views.generic import CreateView

from .forms import TaskForm
from .models import Category, Task

def index(request):
    return render(request, "tasks/index.html", {
        "tasks": Task.objects.select_related("category"),
        "categories": Category.objects.all(),
        "form": TaskForm(),
    })

def category(request, pk):
    current = get_object_or_404(Category, pk=pk)
    return render(request, "tasks/index.html", {
        "tasks": current.tasks.all(),
        "categories": Category.objects.all(),
        "current": current,
        "form": TaskForm(initial={"category": current}),
    })

class TaskCreateView(CreateView):
    model = Task
    form_class = TaskForm
    success_url = reverse_lazy("index")

@require_POST
def toggle(request, pk):
    task = get_object_or_404(Task, pk=pk)
    task.done = not task.done
    task.save()
    return redirect("index")

@require_POST
def delete(request, pk):
    get_object_or_404(Task, pk=pk).delete()
    return redirect("index")

  7. Step 7. The list — ListView

    Now let's replace both index and category with one class. Both pages show the same template; the only difference is which tasks to take. ListView takes the list from the get_queryset() method, so one class serves both routes: on the category page self.kwargs holds the pk from the address.

    tasks/views.py 
    from django.shortcuts import get_object_or_404, redirect
from django.urls import reverse_lazy
from django.views.decorators.http import require_POST
from django.views.generic import CreateView, ListView

from .forms import TaskForm
from .models import Category, Task

class TaskListView(ListView):
    template_name = "tasks/index.html"
    context_object_name = "tasks"

    def get_queryset(self):
        self.current = None
        if "pk" in self.kwargs:
            self.current = get_object_or_404(Category, pk=self.kwargs["pk"])
            return self.current.tasks.all()
        return Task.objects.select_related("category")

    def get_context_data(self, **kwargs):
        context = super().get_context_data(**kwargs)
        context["categories"] = Category.objects.all()
        context["current"] = self.current
        context["form"] = TaskForm(initial={"category": self.current})
        return context

class TaskCreateView(CreateView):
    model = Task
    form_class = TaskForm
    success_url = reverse_lazy("index")

@require_POST
def toggle(request, pk):
    task = get_object_or_404(Task, pk=pk)
    task.done = not task.done
    task.save()
    return redirect("index")

@require_POST
def delete(request, pk):
    get_object_or_404(Task, pk=pk).delete()
    return redirect("index")
    mysite/urls.py 
    from django.contrib import admin
from django.urls import path

from tasks import views

urlpatterns = [
    path("admin/", admin.site.urls),
    path("", views.TaskListView.as_view(), name="index"),
    path("category/<int:pk>/", views.TaskListView.as_view(), name="category"),
    path("tasks/add/", views.TaskCreateView.as_view(), name="add"),
    path("tasks/<int:pk>/toggle/", views.toggle, name="toggle"),
    path("tasks/<int:pk>/delete/", views.delete, name="delete"),
]
    • template_name is our template instead of the default tasks/task_list.html. context_object_name = "tasks" is the list's name in the template (the default is object_list), so the template does not need changes.
    • get_queryset() decides which tasks to show: on the home page all of them, with their categories at once; in a category — current.tasks.all().
    • get_context_data() adds what is not part of the list to the template: the categories for the links, the current category and an empty form.
    • toggle and delete stay functions: they need no template or form, and five lines of a function are clearer than a class. Classes pay off where the work is routine.

    Expected result

    System check identified no issues (0 silenced).

    The pages look and work as after step 6, but there is less code. ListView answers only GET: if a form that posts to the home page is left somewhere, the server will answer 405 (see common errors).

  8. Part 3. Tests

    Step 8. Test the views

    Replace the whole tasks/tests.py. TestCase creates a separate empty database for the tests and rolls back the changes after each test, so your tasks are safe. setUpTestData creates the categories and three tasks once for all tests in the class.

    tasks/tests.py 
    from django.test import TestCase
from django.urls import reverse

from .models import Category, Task

class TaskViewsTests(TestCase):
    @classmethod
    def setUpTestData(cls):
        cls.study = Category.objects.create(name="Учёба")
        cls.home = Category.objects.create(name="Дом")
        Task.objects.create(title="Сдать лабораторную", category=cls.study)
        Task.objects.create(title="Вынести мусор", category=cls.home)
        Task.objects.create(title="Без категории")

    def test_list_shows_all_tasks(self):
        response = self.client.get(reverse("index"))
        self.assertEqual(response.status_code, 200)
        self.assertTemplateUsed(response, "tasks/index.html")
        self.assertEqual(len(response.context["tasks"]), 3)

    def test_category_shows_only_its_tasks(self):
        response = self.client.get(reverse("category", args=[self.study.pk]))
        self.assertContains(response, "Сдать лабораторную")
        self.assertNotContains(response, "Вынести мусор")

    def test_unknown_category_is_404(self):
        response = self.client.get(reverse("category", args=[999]))
        self.assertEqual(response.status_code, 404)

    def test_create_saves_task_and_redirects(self):
        response = self.client.post(reverse("add"), {"title": "Полить цветы", "category": self.home.pk})
        self.assertRedirects(response, reverse("index"))
        self.assertTrue(self.home.tasks.filter(title="Полить цветы").exists())

    def test_create_rejects_empty_title(self):
        response = self.client.post(reverse("add"), {"title": ""})
        self.assertEqual(response.status_code, 200)
        self.assertIn("title", response.context["form"].errors)
        self.assertEqual(Task.objects.count(), 3)

    def test_list_needs_same_queries_for_any_number_of_tasks(self):
        for number in range(10):
            Task.objects.create(title=f"Задача {number}", category=self.study)
        with self.assertNumQueries(3):
            self.client.get(reverse("index"))
    Terminal

    • CreateView saves a task with a category and redirects to the list; an empty title is not saved.
    • assertNumQueries(3) watches for the N+1 problem: the home page makes exactly three queries for any number of tasks — the tasks with their categories, the categories for the links and the categories for the drop-down list.

Test yourself

Answer in your head first, then open the answer.

Why does the ForeignKey have null=True?

The database already held tasks from the first project, and they have no category. null=True allows an empty value in the category_id column, so the migration went through without questions. Without it makemigrations would demand a default value for the old rows.

What happens to the tasks if you delete the “Дом” category?

The tasks stay; they just lose their category: that is what on_delete=models.SET_NULL says. The deletion returns (1, {'tasks.Category': 1}) — one category and not a single task deleted. With CASCADE the category's tasks would be deleted too; with PROTECT Django would not let you delete a category that still has tasks.

How is select_related different from prefetch_related?

select_related joins tables in one SQL query (JOIN) and suits the case when each record has one related object: a task has one category. prefetch_related runs a second query and distributes the results among the objects in Python — it is needed for the reverse relation and for many-to-many, for example to show all tasks of each category.

Why, after switching to ListView, does a form posted to the home page get a 405 response?

ListView only answers reading — GET (and the service methods HEAD and OPTIONS). To POST it answers “Method Not Allowed”. Saving now lives in TaskCreateView at /tasks/add/, and that is where the form must be sent.

Why did we set context_object_name = "tasks" in ListView?

By default the list reaches the template as object_list and task_list. Our template from the first project loops over tasks, and one line in the class saves us from editing the template.

Common errors and how to fix them

The messages are shown exactly as Django 6.1 prints them. Click an error to see the fix.

«no such column: tasks_task.category_id»

django.db.utils.OperationalError: no such column: tasks_task.category_id The model already knows about the category field, but the database table has no such column yet. Do step 2: python manage.py makemigrations and python manage.py migrate.

makemigrations: «It is impossible to add a non-nullable field 'category'»

It is impossible to add a non-nullable field 'category' to task without specifying a default. This is because the database needs something to populate existing rows. The field has no null=True, and the table already has tasks: the database has nothing to put into their new column. Choose option 2 (Quit and manually define a default value in models.py), add null=True, blank=True to the field as in step 1, and run makemigrations again.

«'Category' object has no attribute 'task_set'»

AttributeError: 'Category' object has no attribute 'task_set' Django gives the reverse relation the name task_set only while the ForeignKey has no related_name. Ours has related_name="tasks", so a category's tasks are category.tasks.all().

“Method Not Allowed (POST): /” and a 405 response

Method Not Allowed (POST): / The add form is sent to the home page, which is now a ListView that accepts only GET. Check the form line in index.html: <form method="post" action="{% url 'add' %}"> (step 6).

«TemplateDoesNotExist: tasks/task_form.html»

django.template.exceptions.TemplateDoesNotExist: tasks/task_form.html CreateView shows this template when the form fails validation or when /tasks/add/ is opened. Create tasks/templates/tasks/task_form.html from step 6 — the name is the model name plus the _form ending.

«Reverse for 'add' not found»

django.urls.exceptions.NoReverseMatch: Reverse for 'add' not found. 'add' is not a valid view function or pattern name. The template refers to the add route, but mysite/urls.py doesn't have it. Add the line path("tasks/add/", views.TaskCreateView.as_view(), name="add").

Test: “AssertionError: 15 != 3 : 15 queries executed, 3 expected”

AssertionError: 15 != 3 : 15 queries executed, 3 expected The home page has the N+1 problem again: select_related("category") disappeared from get_queryset, or the template uses another relation that was not loaded in advance. Bring select_related back as in step 7.
